A test harness of about 25 tests graded on physical invariants, not exact values.
Stack

Details

About

FlowNode: guesses are cheap, checks are cheaper

The problem. My partner from True Bots is building AI-enabled engineering simulation software. The existing simulation software is very expensive and hard to use, even though the formulas behind it are public. I took the AI subsystems and the chat, with a focus on running local models, which are limited by the hardware they run on.

What I built. A query's goal is a physically accurate thermal system. So I designed the loop so that guesses come easy and checking them is inexpensive: the harness iterates until it produces a reasonable system that the app can diagram and simulate. That lets a weaker local model reach a correct answer by taking more turns.

Around it: model suggestions that fit the machine's video memory, adaptive context, cache reuse between turns, local-first chat history, structured-output adapters for local and cloud models, and Model Lab, an in-app benchmark that runs models through a gauntlet and grades them against known answers on physical invariants.

What happened. 32 commits and about 38,000 lines between June and September 2026. The product is in development.

What I learned. Local AI is limited by its hardware, so design around the limit: make guesses easy, make checking them inexpensive, and let the harness iterate until the answer holds up.

About

Training Studio: the control panel True Bots trained on

The problem. While training ML agents, we kept going back to the command line and typing long strings of parameter-rich flags. It was really slowing us down, but it was all programmatic.

What I built. A GUI that works directly with the YAML configs, and a way to drive the launch controls that is more intuitive, repeatable and, most importantly, automatable. It came to 21,000 lines that I hand-rolled piece by piece:

  • a live, interactive interface for the YAML training configs;
  • a script that extracted the validation rules from ML-Agents itself, so they followed new versions instead of drifting;
  • a validator that checked the machine and the training environment against them: hardware, platform, paths and the ML components;
  • an environment builder that built the right environment when one wasn't there;
  • run launch, a queue, and live monitoring.

What happened. Our core team of three trained on it from 2024 into 2025.

What I learned. Build for the automation you can see coming. I gave Training Studio command-line and API entry points from the start, because we expected LLMs and agents to drive training before that was a common thing.

About

LLM Bridge: letting a language model play the game

The problem. A separate problem from Training Studio's. Turn-based strategy games aren't bound to real time, and they get more out of playing against more intelligent opponents: language models.

What I built. A bridge that uses plugins to work with game engines (Unity so far, with a C# plugin) and pipes structured data back and forth, with extra checks and considerations along the way. A Python tool opens the channel to a local or frontier model. You pick the provider and the model, choose the game and its rules, and the bridge turns the board into something the model can read, sends the model's move back to the game, checks it against the legal moves, and logs every match.

Where it stands. Built at True Bots, and running again on current local models.

DesktopOpener: tools to build up

The problem. I've been hooked on software since AOL, when I found out you could download new programs that did new things. And every time a computer crashed, I wanted one click that would reopen every app and put each one back exactly where I had it.

What I built. Programming had always been a hobby. I taught myself to program my graphing calculator from its manual, but applications on a PC were out of reach. When LLMs arrived, at the right moment in my life, I taught myself Python, and this was the first project: every piece I needed to take control of my desktop. Open apps, place them, do it again reliably, save the list, open several lists at once.

Every time I hit something I couldn't do, I built the tool for it, and each one became part of DesktopOpener. I needed to measure pixel distances on screen, so I built my own ruler. I got fascinated by Python's live console, built my own, and started on a way to multiplex running scripts. The background workers I imagined never arrived, but many of the apps now run quietly from the system tray.

Where it stands. 382 commits since October 2023: the app, eleven tools and a shared set of utilities, about 120,000 lines of Python with its own tests. It is still a work in progress. I want it on every machine I use, which means cross-platform support and more testing.

What I learned. Build the tools you need to build the things you really want. Each tool I built for DesktopOpener made the next thing possible.

SK's Super Slick and Stealthy Save Saver: my first program for someone else

The Tontec screen: an AI agent finally fixed it

The problem. Years ago I bought a Tontec touchscreen add-on to go with a Raspberry Pi and an acrylic case. The screen, its software and its instructions were always clunky. I think it worked exactly once; then I changed something, it stopped, and troubleshooting it was beyond me at the time. The screen and the Pi sat abandoned.

About

Moonbase: our own home terminal

The problem. My partner and I have a bunch of mismatched smart-home devices. The apps are fine, but we wanted one hub for all of it. I had the old Raspberry Pi and its touchscreen, and the Pi couldn't run any of the modern home hubs. So, again, I built my own.

What I built. A touchscreen home terminal in Python and pygame, with a hand-rolled interface in the style of a starship console. That part was fun. Every screen is built from a display contract, so the same widgets draw into two different frame layouts without knowing which one they're in.

The colors carry meaning, and that's the clever bit. Each theme is a closed set of colors from one era of that console look; nothing outside the set ever appears on screen. Each system gets its color by a fixed rank on a living-to-machine axis: people first, then lights, climate, hubs, calendar, robotics, cameras, network and system. Switch themes and every color changes, but the lights are always "the lights color" and the cameras are always "the cameras color". Status colors come from the theme's own set too. On top of that: contextual menus, and a red button on the case that turns the backlight on and off or shuts the Pi down cleanly.

Where it stands. A work in progress; some services aren't connected yet. But I can touch my lights and stop the Roomba faster, and more pleasantly, than ever.

What I learned. When nothing off the shelf fits the hardware you have, build the hub you actually want, and make it a pleasure to touch.
